### Encryption options and trade-offs

These are design choices, not instructions to alter existing files. Selection must follow a threat model and named key/recovery owner. [OWASP cryptographic-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) supports minimizing data and choosing protection layers and key separation to match threats.

| Option | Protects against | Does not protect against / compatibility cost | Recommendation |
| --- | --- | --- | --- |
| OS full-disk/volume encryption: BitLocker/Device Encryption on Windows; LUKS or approved equivalent on Linux | Offline disk theft/loss/decommissioning when keys are unavailable; files and sidecars on covered volumes. | Mounted/unlocked OS, malware/admin access, API/XSS compromise, plaintext synced/uploaded files or copies on other volumes. Existing hardware/key status unknown. Recovery keys and additional volumes need separate custody/coverage. | Preferred first storage layer for a local prototype, combined with nonsynced paths/ACLs. No SQLite schema change. Device-owner verification/enabling is a separately approved operation, not an automated repository fix. See [Microsoft BitLocker](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/). |
| Whole SQLite database encryption, e.g. SQLCipher | A copied encrypted DB and covered journal pages without its key; useful when live database copies are a specific threat. | App/runtime that has the key, plaintext exports/memory, metadata and some temporary files. Requires compatible native driver/build, key bootstrap, SQLAlchemy/Alembic/backup-tool integration on Windows and Linux. Stock SQLite is not SQLCipher and a silently ignored PRAGMA is not encryption. | Optional separate local research/design spike, not the first interview-demo patch. No new dependency or file conversion approved. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/) requires attention to unencrypted temporary stores, not just the main file. |
| Application-layer authenticated field encryption | Selected values in DB-only leaks/backups when application keys are held separately from DB administration. | Authorized application responses, compromised app/KMS identity, browser/API attacks, exposed dates/IDs/indexes and fields not encrypted. Changes validation, equality/filtering, JSON histories, analytics and export paths; significant risk/complexity. | Defer unless DB-operator separation is an explicit requirement. Use a maintained authenticated-encryption library, per-value nonces, version/key IDs and owner/record/field-bound associated data; no custom cryptographic primitive. Cover historical values as well as current fields. |
| Encrypted exports/backups | Copies intercepted/lost in off-host/removable/cloud storage, provided encryption happens before transfer and keys are separate. | Earlier plaintext downloads/staging, recipients after decryption, compromised source host, unauthorized export or unrecoverable lost keys. Current browser JSON export is unchanged. | First portable-copy control before any real-data workflow. Prefer an approved recipient-based streaming backup/export process; rehearse only synthetic round trips. Adding an encrypted UI export is a separate product change, not implied by this plan. |
| Hosted PostgreSQL/managed storage encryption with KMS | Lost volumes, database storage/snapshots and off-host backups within configured encryption boundaries. | Authorized database/app/admin reads, plaintext logs/exports or compromised KMS permissions. PostgreSQL TLS `verify-full` protects transit, not disks; upstream PostgreSQL is not assumed to provide built-in transparent at-rest encryption. | Future hosted baseline: verified storage/snapshot/backup encryption plus TLS, restricted roles and KMS access. Extra application encryption only if the threat model needs it. [PostgreSQL encryption options](https://www.postgresql.org/docs/current/encryption-options.html). |
| Key management, required for every encrypted option | Key separation, scoped access and recoverable rotation can limit a stolen-copy breach and key-loss outage. | A key next to the data, a compromised process entitled to decrypt, or loss of every recovery copy defeats the intended boundary. | Local: reviewed OS-protected vault/recovery custody; not a key in SQLite, source, VITE variables, shell history or the same synced folder. Hosted: KMS/HSM-backed envelope keys, separate runtime/admin/backup identities, environment-specific versioned keys and value-free access audit. Keep old decryption versions until approved retention expires; test recovery before rotation. |

Recommended scope now: **retain synthetic-only operation; plan local OS/storage/copy controls; remediate installer bootstrap first after approval**. Do not add field encryption or change SQLite format merely to mark a checkbox closed. Full-disk encryption alone cannot close SP4-01's sync/export/recipient-copy risks. No encryption option supplies authorization, research consent, anonymization or clinical validation.

### SQLite, recovery and workflow compatibility risks

- **Existing data remains untouched.** A future conversion requires a separate target-specific authorization after synthetic rehearsals, a restricted consistent recovery copy, stopped/quiesced writers and verification of the intended source/target by the owner. Ordinary copying a live main SQLite file may omit current WAL transactions. Do not run any of this during planning.
- For SQLCipher, plan export into a **new** encrypted target, not in-place conversion, rename or setting a key on stock SQLite. Verify encrypted capability and a schema read with the correct key; wrong/missing key must fail closed, with no fallback to creating an empty/plaintext database. [SQLCipher API](https://www.zetetic.net/sqlcipher/sqlcipher-api/#sqlcipher_export) says plaintext conversion uses export; `rekey` is for already encrypted databases. Preserve schema revision, constraints, foreign keys, account ownership including NULL legacy rows, exact timestamps, revision chains and fixture markers. Check metadata such as `user_version` separately; export is not a blanket guarantee of equivalent file settings.
- Readiness, auth bootstrap, pooled connections, migrations, privileged research CLI and backup tools must all use the correct driver/key boundary. Plan synthetic create/read/update/delete, two-account isolation, journaling, concurrent writer/crash recovery, wrong-key/tamper, rotation and restore tests; include Windows Python 3.13 and Linux wheel/native-build availability. Current in-memory SQLite tests would not prove encrypted-at-rest behavior, so a separate temporary encrypted-file integration suite would be required. No such tests ran now.
- Field encryption would need explicit new versioned schema/serialization and all historical JSON/research paths reviewed; stable date filtering/uniqueness, numeric aggregation, redaction and export semantics must survive. Dual-read/copy-on-write or staged backfill designs carry plaintext/resumption risks and require a separate migration proposal. No existing migration is to be edited retroactively.
- Lost keys can mean permanent loss. A recovery drill must restore a synthetic encrypted backup to a different empty target, validate record/history equality and owner isolation, and invalidate restored sessions before serving. Retain required old key versions securely, protect recovery custody from the same cloud compromise, and never log keys/rows. Disk encryption and backup encryption have different recovery keys and must not be conflated.
- Rollback must pair code, driver/schema, key version and the validated pre-cutover snapshot. Stop/fence writes before switching; writes made after cutover require reconciliation, not silently discarding them by restoring an older snapshot. Keep the original restricted target until an explicit retention decision; do not restore plaintext into a public runtime or turn off encryption/TLS to recover service. Existing plaintext copies remain a residual risk until separately authorized retention/erasure completes.

## Threat model and boundaries

Assets: account credentials, opaque session/CSRF tokens, health observations and episode history, contacts/support preferences, revision journals, consent receipts and private downloads. Actors include anonymous clients, a malicious account holder guessing another record ID, an external website attempting CSRF/CORS abuse or local DNS rebinding, a misconfigured proxy/operator, and a compromised dependency/build source. A database/host administrator, browser extension, stolen unlocked device or downloaded-file recipient is outside application ownership enforcement and needs separate controls.

| Boundary | Controls reviewed / remaining trust |
| --- | --- |
| Browser to API | Cookie session, in-memory CSRF token, exact origins, source Host, TLS in production, session expiry/logout. CORS is not authentication. A trusted frontend origin or XSS can act with its user's authority. |
| API to database | Session-derived owner on all health handlers, foreign object checks, parameterized ORM, no SQL echo, hidden parameters, transactional revisions and account erasure. Authentication does not encrypt files or constrain privileged offline CLI/database access. |
| App to research preparation | Explicit authenticated POST and literal consent, fixed local-download scope, allowlisted numeric history, no independently verified outcomes and no research enrollment. Caregiver consent is separate. |
| Download to device | Fixed attachment filename, no-store, object URL revocation, explicit user action. Browser cache settings do not erase saved downloads, OS backups, screenshots or shared copies. |
| Deployment/configuration | Environment settings are server-controlled; browser `VITE_` values are public. Proxy trust, DNS/certificates, managed secrets, frontend hosting headers and production database operations require review. |
| Dependencies/tooling | Exact lockfiles plus advisory checks; tooling runs locally with dependency metadata only. Registry/advisory integrity, platform binaries and compromised build systems are not proved safe by a zero-result scan. |

## Remaining risks and production blockers

These are known limitations or potential risks, **not newly proven exploits**:

1. No managed HTTPS deployment, independent penetration test, production PostgreSQL/TLS execution, disk/backup encryption, key management, retention purge/restore-erasure verification or disaster-recovery/incident exercise. Proxy trust and production frontend CSP/security headers require host-specific verification.
2. Authentication throttling is process-local and can reset on restart or be multiplied across workers; high-cardinality keys and expensive password work need shared bounded rate limits, request/body/time limits and resource controls. No tested distributed defense, staff MFA, account verification/recovery or session/device management.
3. Administrators can access files/CLI and alter application-enforced history; no tamper-evident immutable storage. Legacy episode/wellness edits lack full historical versions. Extensive unpaginated histories/exports need load testing and resource limits. No raw-error logs means production monitoring needs approved value-free counters and incident correlation.
4. Private exports and backups persist outside account deletion. No automatic revocation of downloaded files; no claim of automatic de-identification. Browser/OS extensions, physical access and accidental user sharing remain outside app control. Retention/withdrawal controls must map every copy.
5. No durable research enrollment, independently verified onset/coverage journal, appointed institutional PI/controller, approved protocol/ethics/privacy review or lawful transfer grant. Park remains NO-GO for strict next-24-hour onset evaluation; N1-Headache contact/publication routes do not grant access. Sprint 13's pilot remains a proposal, not an approved study.
6. Synthetic tests and point-in-time advisory scans are incomplete evidence. Screen-reader/real-device comfort, production load/concurrency, dependency authenticity, privileged access and cross-account attack testing need independent review. No clinical effectiveness, diagnosis/treatment advice or prediction readiness is asserted.

Required next steps: independent security/privacy review; institutional ownership and threat-model sign-off; deploy only after managed secrets/storage/TLS/proxy, shared abuse defenses, recovery and retention/incident controls are implemented and verified; separately authorize research enrollment/evidence infrastructure and ethics review before any real participant collection. Do not bypass the [research readiness gate](RESEARCH_READINESS_GATE.md) because this test suite passes.
