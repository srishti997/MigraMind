# Sprint 9: prospective collection foundation

No forecasting model is trained, loaded or deployed. Collection counts do not establish clinical readiness, causal triggers, predictive accuracy or research enrollment. Use synthetic records in this local prototype.

## Use and migration

From Overview choose **Check in today**, or open **Daily status**. Choose migraine occurred, no migraine, or unknown/not sure and save. All health measurements are optional; default status is explicitly unknown. Expand **Timing and optional observations** for backdating, sleep duration/quality, stress, hydration, routine changes and early symptoms. Use Edit and History beside each report to correct and review it. Settings exports current reports, tombstones and all revisions in schema version 5.

Privately back up before running `./.venv/Scripts/python -m alembic upgrade head` from `backend`. Migration 008 creates only `daily_checkins` and `checkin_revisions`, with account foreign keys, owner indexes and unique owner/date and report/revision constraints. It does not read, assign, copy or update old health rows. A data-losing automatic downgrade is disabled. No migration was run against the existing workspace health database during implementation; users must migrate before using the new page.

`daily_checkins` holds the current JSON values, immutable source date/timezone, first server creation time, revision counter and nullable tombstone timestamp. The values include status, offset-aware event and observation instants, six nullable optional fields and server `status_recorded_at`. `checkin_revisions` stores an inserted snapshot for each creation/correction and a null-valued deletion action, with server availability time and owner. Current-row updates and revision inserts commit in one transaction. Revisions have no update or delete API. This is durable application-enforced append-only history, not database-administrator-proof or cryptographically tamper-evident storage.

## Time and missingness contract

- `date` is the user-selected local calendar date; uniqueness is per account/date even during travel. Its IANA `timezone_name` stays fixed. Changing either on edit is rejected. A wrongly dated report can be tombstoned and a report created for the correct date.
- `event_at` is the reported instant the observations apply to. It must fall on the selected source-local date. `observed_at` is the reported instant the person noticed those observations. These are distinct from server `created_at` and revision `recorded_at`; the server cannot independently verify human observation times. Event time must be at or before observation time, and neither may be future-dated. Both require explicit offsets and normalize to UTC while retaining the source IANA zone.
- One report contains one optional observation set for one event/observation time pair. It is not a multiple-events-per-day observation stream. Different-time observations may still use existing wellness and early-symptom forms; those legacy records are separate and lack the new revision guarantees. No original timestamps or audit history are fabricated for legacy data.
- Every full correction reaffirms the submitted status at server `status_recorded_at`, retains the original `created_at`, and adds a complete revision with actual correction availability. Current reporting labels a report retrospective when the current version was saved after its source date. An originally same-day report corrected later is therefore counted as retrospective; its original same-day revision remains available in history. Same-day is a descriptive collection timing category, not proof of prospective ascertainment or a forecast label.
- A no-migraine report saved during its date is provisional indefinitely. Merely crossing midnight does not make it a completed negative. The person must explicitly edit/save the status after the source day ends to confirm the completed day. The original observation/event times may remain unchanged; server confirmation time records when the whole-day statement became available.
- Local-day completion uses IANA midnight boundaries, including 23/25-hour DST days. APIs receive actual offset-aware instants, so repeated wall times can be represented distinctly. Browser inputs reject nonexistent device-local times and preserve unchanged saved instants (including seconds, offsets through UTC normalization and repeated-hour selections). A changed ambiguous wall time follows the browser's offset choice; a dedicated fold selector is not implemented. Device timezone labels are separate from the immutable report source zone while editing after travel.
- Blank health fields are null, explicit zero is retained, and unknown status is a real report. Missing reports are always unknown. Text blanks are null in the browser; APIs may accept an explicitly empty string as a known empty response. Nothing imputes exposure values or establishes a proven trigger.

## Episode and wellness boundaries

Daily status never creates, edits or removes a diary episode or older wellness status. A no-migraine report with any overlapping diary episode is a discrepancy, including zero/unrated episodes. Exact midnight ends exclude the next date; unknown ends count the onset date only. Legacy date-only episodes remain date-only. A migraine report without a diary episode is shown for review rather than fabricating an onset. Different explicit statuses on the older wellness form also produce a discrepancy. No reconciliation or research label is inferred automatically.

## APIs, privacy and retention

All routes use existing cookie authentication, session-bound read headers, origin/CSRF write checks, no-store middleware and server-selected ownership. Caller-supplied owner fields are rejected. IDs belonging to another account return 404. New collection writes use the existing process-local limiter (120 attempts per account per 15 minutes); this remains unsuitable as a shared multi-worker limiter. Validation/database exceptions use the existing redacted handlers; no request bodies or health values are logged.

| API | Behavior |
| --- | --- |
| GET `/api/daily-checkins` | Current reports; `include_deleted=true` adds null-valued tombstones, never other accounts. |
| POST `/api/daily-checkins` | Create an account/date report; exact repeated submitted values return the existing row without adding a revision. Different duplicate values return 409. A concurrent unique-key collision returns 409 for safe reload/retry. |
| PUT `/api/daily-checkins/{id}` | Full correction with required `expected_revision`; compare-and-swap plus unique revision constraints prevent lost updates. Stale versions return 409. Deleted reports return 410. |
| DELETE `/api/daily-checkins/{id}?expected_revision=N` | Revision-checked tombstone and deletion audit; repeated deletion is idempotent. |
| GET `/api/daily-checkins/{id}/history` | Account-only chronological revision values, including after tombstoning. |
| GET `/api/v1/collection-quality?timezone_name=UTC&days=30` | Descriptive quality; days is 7–90, invalid IANA zones rejected. No historical cutoff or owner override. |
| GET `/api/export` | Schema 5 includes both new tables, including sensitive prior values. Store privately. |

Record deletion clears current values but retains earlier sensitive values in private history. Tombstones reserve the account/date and cannot currently be restored or replaced on that date. The deletion confirmation and page explain this. No separate revision-erasure API or automatic retention expiry exists. Account deletion hard-deletes revisions first, then daily rows, then the account, in the existing deletion transaction. Other accounts and unclaimed legacy rows remain untouched. Private exports/backups are independent copies and are not remotely erased by account deletion; production backup expiry, legal retention and consent policies require review before deployment. Access logs remain disabled in the documented server launch; infrastructure logging remains a separate deployment concern.

## Collection quality and research boundary

Overview > AI Insights > **Daily collection quality** makes an explicit read-only request. The last 30 dates include today. Observed days include explicit unknown reports. Unknown days comprise absent and explicitly unsure dates; disagreements are reported separately and do not become qualifying negatives. Completed no-episode days require server confirmation after source-day end and no episode/wellness discrepancy. Same-day/current-version versus retrospective counts, missing fields, corrections, tombstones and discrepancies are shown. Missing-field denominators are current reports, including reports in other zones; corrections include deleted reports in the window. Counts use report event dates, not correction dates.

Coverage only combines reports whose source zone exactly matches the requested reporting zone. Other-zone reports are counted separately, without remapping calendar dates. Equivalent timezone aliases are conservatively kept separate. The older readiness panel continues its existing legacy-data calculation; the new quality panel is separately labeled and does not silently change that research adapter or descriptive comparisons. Newly audited optional values are not injected into training/preparation. All forecasts remain unavailable and established prospective-label counts remain zero. There is no count threshold that enables training or implies clinical readiness.

Future evaluation must have explicit research consent, reviewed provenance, a predefined at-risk schedule, complete surveillance intervals, a full elapsed-24-hour outcome horizon plus reporting lag, and documented discrepancy adjudication. Reconstruct features from the latest revision strictly available before cutoff; apply tombstones and exclude later corrections even when their event timestamps are earlier. Do not use final current-row exports as historical knowledge. Version legacy sources before including them. Freeze outcome labels after the full horizon/reporting lag; enforce chronological purging, training-only preprocessing, validation-only threshold selection, class-supported calibration/discrimination metrics and independent prospective validation. See the existing foundation and audit documents; no model experiment was invoked here.

## Verification and known limits

Automated tests use synthetic isolated databases, including migrations from 007, two-account isolation, CSRF, duplicates, chronology validation, DST folds, missing versus zero, retrospective edits, revision conflicts, tombstones, exports, account erasure and provisional-negative reconfirmation. Browser coverage uses a separate synthetic SQLite database, never the existing user database. See README for final exact results.

PostgreSQL execution, real screen readers/devices, comfort during a migraine, large-history performance, distributed rate limiting, backup deletion, independent security review, complete surveillance and clinical validity remain unverified. Listing/history have no pagination; query costs and retention need review before long-term production collection. This foundation does not make the local prototype suitable for real health data or establish a clinically validated dataset.
